# Program Chair portal

The administrator assigns the `program_chair` role and its college in Access Accounts. A faculty member keeps the same shared login and can choose or switch to Program Chair. The portal checks the active account, role, college, and campus on each request. Administrator reassignment takes effect on the next request.

The Chair sidebar keeps Dashboard at the top, followed by the visible Faculty Management heading (College Faculty, Faculty Profiles, Faculty Workload, Faculty Evaluation), then Academic Management (Programs, expandable Curriculum, Students). A separated Reports menu contains Faculty & Student Summary, Student Statistics, and Faculty Statistics. Curriculum and Reports expand automatically for their active pages; prospectus previews keep Curriculum Browser highlighted. This grouping applies only to Program Chairs, while the Dean's original navigation remains intact. `program-chair/*.php` delegates to the existing Dean views. The shared sidebar and navbar display the actual active role. Shared JavaScript uses dedicated Chair endpoints, which enter the existing scoped handlers without changing the user's role. Viewing terms are stored separately for Dean and Chair.

Curriculum adds a Curriculum Browser and Curriculum Builder to the Chair sidebar. These reuse the administrator's prospectus screens and handlers with the Chair's navigation, local Select2/SweetAlert assets, and dedicated scoped endpoints. The Chair browser includes empty curriculum versions and shows View, Manage, and More for each row. More contains Edit Details (CMO/effectivity), Move to Another Program, and a separated Delete Prospectus action with the existing confirmation. Copy remains in the builder. Menus use fixed Popper positioning to avoid clipping inside the responsive table and are disposed when rows refresh. The administrator retains its existing browser actions. The builder creates or loads curriculum versions, adds/removes year and semester sections, and adds, edits, or removes subjects with lecture/laboratory hours, calculated units, ordering, and prerequisites. Manage loads the selected version directly. The shared university subject masterlist supplies available subjects; prospectus edits leave that masterlist unchanged.

Every curriculum request reloads the active Chair role and college assignment from the account. Programs, curriculum versions, year/semester sections, and subject rows are checked against that college on the server. Copy and transfer validate both the source and destination, preventing access across colleges even with forged IDs. Direct administrator write routes remain unavailable to Chair sessions. Writes require CSRF and lock the current account, role assignment, college, and target records; successful shared-handler responses commit the enclosing transaction, while failures roll back, including a failed multi-row copy. Curriculum version management is independent of the navbar's selected scheduling term. Full prospectus deletion follows the administrator's existing confirmation and cleanup of its generated offerings and schedules.

College Faculty follows Scheduler's Faculty Assignment per College page: the same desktop table/mobile cards, search and pagination, searchable Add Faculty dialog, designation dialog with No designation, employment classification dialog, removal confirmation, and Copy Previous List preview. The interface was adapted into Chair files; the original Scheduler page is unchanged. It creates or reactivates a current-term `tbl_college_faculty` assignment from the shared active faculty directory. Classification is stored on `tbl_faculty`; designations use `tbl_faculty_term_designations` for the selected current term, as they do in Scheduler. No separate faculty copies are created. Active current-term and legacy assignments are treated as duplicates; historical terms are for viewing only. Server checks enforce the current term, administrator-assigned college, active faculty, and CSRF token.

Removing deletes only the college-list entry and retains the faculty record, appointments, schedules, and prepared workloads. Copy Previous List uses the same source-term catalog and preview queries as Scheduler, stages a Chair-specific preview token, and copies only selected eligible faculty into the current term. It retains the source term's designation unless a current appointment was already selected. Copy confirmation rechecks source membership, college access, faculty status, and the current term, skips newly added duplicates, and consumes the token to prevent replay.

The faculty dialogs use the same Select2 version as Scheduler, bundled under `program-chair/vendor/select2` with its MIT license, and the existing local SweetAlert2 asset. These dialogs do not require a CDN connection.

The faculty name column shows at most four login details on desktop and mobile: Login active/inactive, Faculty when the `professor` role is active, Scheduler when the `scheduler` role is active, and Login Access. The name is on the first line, login labels on the second, and Login Access on the third. The label line reserves space even when a faculty member has no login account. Other roles, account credentials, and administrative labels are omitted. Search matches faculty name, designation, and employment classification. The designation, employment classification, and remove actions have full labels and occupy three separate rows.

Login Access creates a shared login for an assigned faculty member who has no account, or edits an existing linked account's Faculty/Scheduler roles and permitted default workspace. Existing account credentials and unrelated roles are excluded from list and account API responses. The email input appears only when creating a new login; existing-account edits do not require sending an email. Administrator-controlled roles and defaults are preserved on the server, including inactive roles. A protected default workspace is omitted from the editor, and protected shared login status remains read-only. Explicit role assignments take precedence over outdated or empty primary-role values. Accounts with a different home college or other college access show a read-only dialog explaining the scope restriction.

A new login requires an unused institutional email and follows the administrator's Google account setup; an existing login keeps its email and credentials. A Scheduler receives access only to the Chair's assigned college. The explicit faculty link is retained when Scheduler is the sole selected editable role. Active/Inactive status can be changed on accounts with only Faculty/Scheduler roles. Checks run on the server for every save, require the current term and CSRF, and reject stale edits. Account, editable role, faculty-link, and college-access changes commit together or all roll back.

Existing Scheduler files and scheduling/workload calculations are unchanged. The two new Chair chart/matrix endpoints retain the Dean read-only implementation with Chair authorization; the integration suite verifies these copies differ only in authorization. Faculty additions do not assign classes, change workloads, or edit schedules. No SQL migration is required on the current schema.

The Administrator Prospectus Browser filters Campus, then College, and automatically lists all curriculum versions in that college, including empty versions. Program is an optional narrowing filter, with the curriculum count after each program label. Inactive campus, college, and program records remain identifiable for viewing existing curricula. The Chair browser displays only the optional program filter and automatically derives its campus and college from the authorized account; it never offers campus or college selectors. College-wide rows include Program/Major, and every action uses that row's actual program and prospectus IDs. Filters refresh counts after mutations, ignore outdated AJAX responses, and never modify the scheduling term, account college, section curriculum assignments, generated offerings, or workloads. Existing write actions retain their existing behavior.

The Chair Prospectus Builder first lists every prospectus version for the selected program, including empty versions, ordered by effectivity year. Load/Reload selects an explicit version and displays its program, CMO, and effectivity above the existing year/semester editor. Create New Prospectus opens a separate form and loads the new empty version; an existing program/CMO/effectivity combination offers to load the existing version. Copy uses the loaded version as its fixed source, allows the same or another permitted college program as destination, and loads the copied destination's full header and structure. Program changes clear the editor, late version/header/structure responses are ignored, and pending create/copy requests cannot be submitted twice. This Chair interface reuses the existing read/save/copy actions and permissions; the administrator builder and scheduling/workload rules retain their existing behavior.

Database fixtures run inside transactions/savepoints and roll back. The browser test renders the real faculty page with intercepted API responses to check adding, designation removal, classification edits, search, copying selected faculty, removal confirmation, limited login details, three-row actions, login status and role edits, errors, duplicates, repeated submissions, refreshed desktop/mobile rows, and historical-term restrictions. The HTTP suite checks the actual installed PHP runtime and request handlers, including the real shared-login chooser accepting a Chair-assigned Scheduler role and rejecting an inactive account. Account tests cover forbidden roles, protected accounts, other colleges, stale edits, invalid email/status/roles, and rollback after a failed role write. Management tests verify that class schedules and workload records are unchanged.

The curriculum CLI/HTTP suite renders all three Chair curriculum pages, compiles their rendered JavaScript, and exercises real read/write handlers with fixtures from two colleges. It covers every supported mutation, invalid CSRF, foreign source/destination/subject IDs, stale or revoked college access, malformed input, duplicate subjects/sections/copies, prerequisite validation, and rollback after an injected copy failure. It also checks the administrator's existing actions and all-college program list, preserves Scheduler read-only permissions, and verifies real account, curriculum, subject-masterlist, schedule, and workload checksums after all fixtures are rolled back.
